# OmniSQL security and database roadmap

OmniSQL should keep its main advantage: connecting an assistant to saved database connections without copying credentials into chat. The immediate work is to make the access controls and result limits consistent, then add accurate metadata and a small number of useful drivers. A driver count does not measure whether a connection is safe or a query result is correct.

The audit covers the first-party server, installer, authentication, tunnels, pools, transaction manager, metadata and result handling, CI, and website. The starting revision was `94165f5`. Disposable PostgreSQL and SQLite fixtures reproduced the reported failures; Docker integration checks now exercise the implementation against seeded services. Dependency advisories are a separate check: both npm audits returned zero known vulnerabilities. That does not rule out application bugs.

## Security findings from the starting revision

The disposable fixture checks reproduced nested credential leakage in connection details, PostgreSQL sequence changes through a read tool, stacked DDL, a DELETE guard bypass, a string accepted as a confirmation, ignored row caps, and ignored PostgreSQL timeouts. They also reproduced a revoked SSH key being accepted when an identical trusted entry exists. These need regression tests tied to the fixes.

Code inspection also identified SQL Server's global pool, inconsistent TLS settings between execution paths, unbounded schema comparison concurrency, missing database and schema qualification in metadata, shared temporary insight storage, and inconsistent large-number handling. Database and table policies must inspect SQL references as well as the selected connection: changing the connection's default database does not restrict qualified cross-database SQL.

The baseline Vitest run passed 223 tests. Including every production source file in coverage measured 40.66% of lines. The server entry point, pools, transaction manager, and query-analysis modules had no coverage in that instrumented run. The separate packed-MCP smoke test is not included in that percentage. The next tests should cover those execution paths and the reproduced failures rather than chase a percentage with mirrored implementation tests.

## Access policy

Keep operator configuration outside assistant tool arguments. Use one authorization path before execution and apply the same policy to discovery, resource reads, query plans, exports, and transaction operations.

A policy should identify the workspace project and saved connection ID, then allow specific databases, schemas, tables, operations, and functions. Deny rules take precedence. Resolve names using the database's identifier rules; do not strip characters and accidentally target another connection. Reject ambiguous connection names and project collisions.

Read-only should be the default for the next major version. Enabling INSERT must not implicitly enable UPDATE, DELETE, DDL, or arbitrary transaction commands. A model-provided `confirm: true` is a tool argument, not human authorization. Unknown policy options, invalid environment values, and unsupported SQL in restricted mode must fail closed.

Table restrictions must cover joins, subqueries, CTE scope, quoted names, views, synonyms, and cross-database references. Column and row restrictions should use restricted database views, column grants, or row-level security. Masking an output cell does not prevent inference through WHERE clauses or aggregates. For the strongest application-level restriction, expose predefined parameterized queries and disable arbitrary SQL.

Use database read-only transactions where supported and least-privileged database accounts everywhere. SQL parsing is one layer: functions, casts, external data access, and database-specific behavior still require database permissions. SQL Server read intent is not a permission boundary. DuckDB read-only files do not disable filesystem and network functions.

## Small shared abstractions

Keep `WorkspaceClient` as the public facade while moving engine behavior behind a small `DatabaseAdapter` contract. An adapter reports capabilities and handles connections, queries, metadata, plans, and cleanup. Shared execution code owns authorization, deadlines, row and byte limits, error handling, and result artifacts. Driver modules should not each implement their own policy.

Use a registry of adapter factories, not a large inheritance hierarchy or a plugin marketplace. Share normalized connection properties, identifier handling, result types, and lifecycle helpers. Keep native transaction handles inside their adapter. Route ordinary queries and explicit transactions through the same pool manager, with target and configuration isolation and bounded queues.

Cache workspace parsing and metadata with explicit invalidation. Lazy resource listing should return connection summaries without connecting to every saved database. Schema search should return a small matching set and fetch details on demand. Add MCP tool annotations and structured results, while continuing to enforce permissions on the server.

## Result handling and performance

Enforce `maxRows` independently of SQL text. Existing LIMIT clauses, CTEs, comments, and identifiers containing `limit` must not bypass it. Add byte and cell limits as well: one large LOB can exceed the model context even when there is only one row. Fetch one extra row when needed to distinguish truncation from an exact-sized result.

For large outputs, return a short preview, columns, row and byte counts, and an opaque result handle. Provide bounded page reads and CSV or JSONL export. Store files in a private directory scoped to the workspace and process, with expiration, quotas, atomic creation, and no caller-chosen arbitrary destination. Keep decimal and 64-bit integer values exact; preserve duplicate column names with positional rows.

Use bounded parallelism for schema queries and release clients on every success, timeout, cancellation, and error path. PostgreSQL statement timeouts, MySQL cancellation, SQL Server request cancellation, Oracle call timeouts, and subprocess termination need driver-specific implementations behind the shared request deadline.

A local PostgreSQL microbenchmark measured 40 one-shot connections against 40 queries on a reused pool. Median latency was 2.069 ms versus 0.058 ms; p95 was 2.668 ms versus 0.087 ms. This measures loopback `SELECT 1`, SCRAM authentication, and no TLS. It is not an OmniSQL end-to-end speedup. A separate ten-process `node dist/index.js --version` sample had median startup of 165.5 ms and p95 of 466.0 ms; one measured process used about 132 MiB peak RSS. Recheck after lazy driver imports and shared pools.

Snowflake, Databricks, Redis, Db2, and Cassandra complete its top ten. This ranking measures public popularity signals, not installed market share.

The AWS MCP repository has 9,789 stars, but it is a collection of many servers. Chat2DB and dbx have 28,321 and 27,091 stars and include MCP as part of broader database applications. Their counts are not directly comparable to a database-only MCP server. The older [Snowflake Labs MCP](https://github.com/Snowflake-Labs/mcp) now marks itself deprecated; follow Snowflake's maintained vendor service when designing that adapter.

Useful early additions are schema search, real indexes and constraints, accurate sizes, private result artifacts, and a compact default tool profile. Add advanced PostgreSQL workload and hypothetical-index tools only after permission checks and extension detection exist. An absent extension or denied statistics view should return an explicit capability result, not invented health data.

## Rust decision

Keep database I/O, authentication, installation, and MCP transport in TypeScript for now. The measured connection overhead and resource-management problems have direct fixes in the current stack.

The useful Rust experiment is a pure SQL-analysis module: accept a dialect and query, return statement classes, referenced objects, and function calls. Compare a JavaScript parser with [sqlparser-rs](https://github.com/apache/datafusion-sqlparser-rs) behind [NAPI-RS](https://napi.rs/) and a portable WebAssembly build. sqlparser-rs explicitly distinguishes syntax parsing from semantic analysis; it does not supply database authorization.

Use a shared adversarial corpus and measure parsing CPU, startup, binary size, memory, and end-to-end latency. Consider adoption only if parsing is a material part of the measured workload and the improvement justifies cross-platform release maintenance. An unavailable native module must never cause restricted mode to fall back to weaker SQL checks. Keep installation through `npx` working without a Rust compiler.

## Validation and release

Use ephemeral containers with loopback-only published ports, generated credentials, synthetic tables and indexes, and cleanup restricted to the test run's containers and volumes. Test PostgreSQL, MySQL, MariaDB, SQL Server, and Oracle independently. SQLite and DuckDB use temporary embedded files. Run the same MCP-level tests against new adapters, including failure and denial paths.

For each PR, run lint, type checking, unit and policy tests, packed-server checks, real integration tests for changed drivers, and dependency audits. Run site checks after documentation or tool-schema changes. Preserve manual npm publishing. Record supported versions and any platform-specific validation gaps before release.
